# Aletheia 失败史与修订纪律

## 为什么要保存失败史？

如果一个项目只保存越来越漂亮的最终稿，它看起来更像宣传材料，而不是研究项目。

Aletheia 应保存错误、反例、废弃机制和版本修订。

这不是削弱项目，而是让外部读者知道：

> 哪些已经确认，哪些只是猜想，哪些曾经错过，哪些仍未解决。

## 失败史包括什么？

失败史至少包括四类内容：

### 1. 被放弃的命题

例如某个理论命题被案例或反例击中，已经不再保留。

记录格式：

```text
原命题：
发现的问题：
反例或证据：
处理方式：
当前状态：
```

### 2. 被修订的定义

例如“谁的需求谁第一责任”曾经被误解为“谁提出需求谁负责”，后来修正为“先判断需求归属，再确定第一责任人”。

记录格式：

```text
旧定义：
问题：
修订后定义：
修订理由：
影响文件：
```

### 3. 失败的机制草案

例如某个责任积分、公共任务或亲职机制，如果发现副作用过大，应记录失败原因。

记录格式：

```text
机制名称：
设计目的：
发现的风险：
失败场景：
是否废弃：
是否保留部分内容：
```

### 4. 尚未解决的问题

不是所有问题都要立刻补成规则。

有些问题应保持未决状态：

- 证据不足；
- 成本不明；
- 受影响者意见不足；
- 反例尚未处理；
- 替代方案尚未比较。

## 修订纪律

### 1. 不用反例自动生成新规则

反例的作用是检验命题，不是自动要求项目不断补条件。

遇到反例时，先判断核心命题是否仍成立。

如果核心命题不成立，应直接修改或放弃，不应无限增加例外。

### 2. 区分修订和补丁

修订是改变命题结构。

补丁是为了保住原命题而增加条件。

如果一个命题需要越来越多补丁才能成立，应考虑降低命题强度或放弃该命题。

### 3. 机制失败不能反向修改原则

如果某个机制不可行，应修改机制。

不能因为机制方便，就削弱人格底线、退出权或基本保障原则。

### 4. 原则冲突必须记录

如果一个新方案与第一原则冲突，应记录冲突，而不是静默合并。
